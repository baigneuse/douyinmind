# 网络视频资料库实现与真实验收

日期：2026-10-23（Asia/Tokyo）。承接 Phase 1 `dfe4da2398ce69c1c71b9dbb1682d6f8f70afd52` 及本地媒体工作台开发。实现分支为 `feature/local-media-ui`；提交与同步状态以该分支的 Git 记录为准，本报告不表示已部署发布。

## 目标与边界

用户调整了优先级：先完善多个平台的网络视频收集、整理、下载与回看，再考虑转写、逐字稿和知识总结。本轮把默认网页入口改为视频资料库；没有新增真实 ASR、embedding 或 LLM 调用。原本地字幕工具和抖音工作区作为次级入口保留。

## 已实现

- 完整分享文字与多行 URL 输入，一次最多 20 条；保存来源时不访问原站，也不自动下载。
- 规范化 URL 去重、来源记录、标题、标签、备注、星标、可逆归档、搜索和平台筛选。
- 显式下载、排队、取消、失败重试、重启中断状态；所有下载记录可查看。
- 成功文件经过大小、时长、完整解码与 SHA-256 检查后发布。本地播放支持 Range 请求，原件可下载导出。
- 失败或取消保留来源和旧的成功媒体。编辑采用版本检查，冲突时保留草稿；播放使用稳定媒体版本，元数据变更不重载视频。
- 网络处理独立于原抖音登录下载流程。不读取浏览器 Cookie、账号配置、模型密钥或代理；没有自动同步收藏夹。

新增后端模块是 `network_library.py`、`network_download.py`、`network_download_worker.py` 和 `/api/network-media` 路由；前端新增 `NetworkMediaLibrary` 页面及独立客户端。复用现有本机工作目录、请求保护和串行后台队列。

另用 Phase 1 已记录来源与许可的公开 Sintel 短片作为下载链路控制样例：

- 固定来源：[原字幕演示仓库视频文件](https://raw.githubusercontent.com/chrisdavidmills/html5-captions-and-subtitles-content-kit/400f234c4dcafb7505f67ee7262f748662d667bf/demo/video/sintel-short.mp4)。许可背景见 [Phase 1 验收](PHASE1_ACCEPTANCE.md)。
- 通过真实 HTTP 下载，**22,306,323 bytes，120,000 ms**。
- SHA-256：`358447f332663e6f3794816e32b8072526fcba8bf8744dc7fb3387afb5b2fceb`，与 Phase 1 原样例一致。
- 完整原件接口 HTTP 200，返回 22,306,323 bytes，重新计算散列一致；`Range: bytes=0-1023` 返回 HTTP 206、1024 bytes。
- 浏览器实际显示画面，`duration=120`、`readyState=4`，播放中 `currentTime=6.200254`；暂停及键盘时间跳转后为 `21.1896` 秒。
- 没有把该控制样例计入用户的四条平台视频成功数。

网页人工流程还验证了标题、标签、备注保存，星标，归档恢复，以及按标题或标签搜索。Bilibili 的人工标题来自用户分享文字，不是未经成功获取的自动元数据。

**用户四条样例的完整视频下载成功数是 0/4；另外的公开直链控制样例为 1/1。** YouTube 的部分数据没有算作成功，不会出现在可播放媒体中。当前 15 分钟上限是工具自己的资源限制；本次证据不能证明增加时限后一定成功，也不能证明该视频永远无法下载。

YouTube 兼容修复包括避免 Windows 大输入管道等待、给本地 solver 输入与输出设限，以及不执行 yt-dlp 后续的外部工具探测。使用固定版本的本地 Deno/EJS，未修改 site-packages、未开启 Deno 的网络/文件权限。最后一次元信息诊断仍记录 `Local solver failed` 警告，具体原因未确定；没有保留足以定位该次退出码和 stderr 的证据，不能声称 n challenge 已修复，也不能断言它就是低速的唯一原因。

## 当前未完成的产品能力

当前网络入口覆盖“保存和整理这些平台的链接”，不等于“这些平台的视频都可以下载”。未实现账号连接、登录状态授权管理、平台全量收藏同步、短长链接全局合并、直播/HLS、云端部署、跨平台搜索或 RAG。默认最高选择 720p，单视频 500 MiB / 2 小时，15 分钟下载时限；不对直链转码降分辨率。

下一步仍应围绕网络收集与下载，按以下顺序完成：

1. **YouTube 下载可靠性**：补充安全的 solver 错误类型诊断；将超时做成合理可配置的任务限制，增加真正的断点恢复与清晰的音视频分轨进度，再用同一条 26 分钟样例验收。当前“重试”从新任务开始，尚不支持断点续传。
2. **抖音、Bilibili 的显式账号连接与访问状态诊断**：账号登录/验证由用户在原站完成，隔离保存授权状态，明确连接与断开；不得默认读取现有浏览器 Cookie。当前工具尚未提供这一连接功能，单纯在另一个浏览器登录不保证匿名下载恢复。
3. **用原样例验收成功文件**：每条都要有可播放完整音视频、来源、大小和散列；分别记录登录失效、取消、网络中断与重试结果。未取得凭证或原站仍拒绝访问的情况继续保持真实阻断状态。

在此之前，不以增加转写和总结功能替代下载体验的缺口。现有抖音登录流程不可直接当成无副作用的账号连接复用，因为它还关联旧收藏同步行为。

旧收藏夹唯一约束和 Chroma 孤儿块问题仍由既有 xfail 门禁记录，本轮没有恢复或扩大旧抖音批量同步。

使用方法、存储位置和恢复说明见 [网络视频资料库](NETWORK_VIDEO_LIBRARY.md)。
